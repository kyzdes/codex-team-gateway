# codex-team-gateway

Совместная среда для команды, работающей с [Codex CLI](https://developers.openai.com/codex/cli)
над одним проектом параллельно. Даёт каждому участнику команды личный
веб-чат в браузере, из которого можно напрямую задавать Codex вопросы по
сервису и просить доработки — Codex выполняет их автономно (правит код,
коммитит, деплоит) в своей изолированной рабочей копии проекта.

Работает на любой Ubuntu-машине: физический сервер (например, Mac mini
под Ubuntu) или обычный VPS.

## Что это даёт

- **Общий доступ без общего терминала.** Не нужно раздавать SSH-доступ и
  делить один терминал — у каждого коллеги свой токен и свой веб-чат.
- **Параллельная работа без конфликтов.** Каждый участник работает в своём
  `git worktree` одного репозитория — файлы не перезатираются.
- **Полная автономность Codex.** По умолчанию настроено на
  `approval_policy=never` + `sandbox=danger-full-access` — Codex сам вносит
  изменения, коммитит и деплоит по запросу любого участника, без запроса
  подтверждения. Это выбор скорости за счёт контроля — см. раздел
  «Автономность и риски» ниже.
- **Аудиторский след.** Каждый запрос и полный JSONL-лог действий Codex
  сохраняется на диск — единственная страховка при отсутствии
  подтверждений в моменте.

## Установка в 2 команды

```bash
curl -fsSL https://raw.githubusercontent.com/kyzdes/codex-team-gateway/main/install.sh | sudo bash
sudo -u codex /opt/codex-team-gateway/setup-project.sh <git-url-вашего-проекта> colleague1 colleague2
```

Первая команда ставит Node.js, Codex CLI, Python-зависимости шлюза,
генерирует токены доступа и поднимает systemd-сервис на порту 8787
(доступен только на `127.0.0.1` — наружу ничего не открывается).

Вторая — клонирует ваш реальный проект и создаёт по отдельному
`git worktree` на каждого указанного коллегу.

Дальше:

```bash
sudo -iu codex
codex login --device-auth   # один раз авторизовать Codex CLI
```

Откройте `/etc/codex-gateway/config.json` — там уже сгенерированы токены
и прописаны пути к worktree-папкам. Отдайте каждому коллеге его токен и
адрес шлюза (см. «Удалённый доступ» ниже).

## Автономность и риски

По умолчанию Codex получает полный доступ к коду, инфраструктуре и
секретам и применяет изменения без вашего утверждения. Это осознанный
выбор скорости. Обязательно сделайте перед реальным использованием:

1. Скопируйте `AGENTS.md.template` → `AGENTS.md` в каждую worktree-папку
   и заполните реальными правилами: команды тестов, что можно/нельзя
   трогать (биллинг, продовые данные), когда обязателен бэкап перед
   миграциями БД.
2. Скопируйте `deploy.sh.template` → `deploy.sh`, впишите реальные
   команды тестов и деплоя. Скрипт уже оборачивает деплой в `flock`, чтобы
   два параллельных запроса от коллег не задеплоили одновременно.
3. Секреты/инфраструктурные ключи лучше выдавать Codex под отдельным
   сервисным аккаунтом с ограниченными правами, а не под вашим личным
   root/admin-доступом.
4. Логи каждого запроса лежат в `logs/<коллега>/<время>.jsonl` — это
   единственный способ разобраться, что произошло, если что-то пойдёт не
   так.

Если нужен более осторожный режим — поставьте в
`/etc/codex-gateway/config.json`:
```json
"sandbox_mode": "workspace-write",
"approval_policy": "on-request"
```
Тогда Codex не сможет выйти за пределы рабочей папки и будет спрашивать
подтверждение в неоднозначных случаях (учтите: в `codex exec`
подтверждения в неинтерактивном режиме автоматически трактуются как
отказ, так что `on-request` там по факту сузит набор разрешённых
действий, а не откроет диалог).

## Удалённый доступ через интернет

Порт шлюза (8787) слушает только `127.0.0.1` — это осознанно, чтобы не
открывать доступ к среде с полным контролем над инфраструктурой прямо в
интернет. Рекомендуемый способ дать доступ коллегам из любой точки —
[Tailscale](https://tailscale.com/download):

```bash
curl -fsSL https://tailscale.com/install.sh | sh
sudo tailscale up
```

Коллеги ставят Tailscale на свои устройства, заходят в ту же tailnet — и
открывают `http://<tailscale-имя-сервера>:8787` из браузера.

Альтернатива без VPN-клиента у коллег — Nginx reverse proxy с доменом и
TLS (certbot) поверх Basic Auth, или Cloudflare Tunnel + Cloudflare
Access с логином по email.

## Структура репозитория

| Файл | Назначение |
|---|---|
| `install.sh` | Установщик: Node.js, Codex CLI, Python-зависимости, systemd |
| `setup-project.sh` | Клонирует ваш проект, создаёт worktree на каждого коллегу |
| `app.py` | Backend шлюза (FastAPI): аутентификация по токену, запуск `codex exec`, история |
| `static/index.html` | Чат-интерфейс в браузере |
| `gateway_config.example.json` | Пример конфига (реальный лежит в `/etc/codex-gateway/config.json`) |
| `AGENTS.md.template` | Шаблон правил для Codex — обязательно заполнить под ваш сервис |
| `deploy.sh.template` | Шаблон деплой-скрипта с блокировкой (`flock`) |
| `systemd/codex-gateway.service` | systemd-юнит для запуска шлюза как сервиса |

## Как это работает внутри

- Каждое сообщение от коллеги выполняется через `codex exec --json` в его
  персональной worktree-папке.
- Первое сообщение создаёт новую Codex-сессию (`thread_id`), все следующие
  сообщения того же коллеги продолжают её через `codex exec resume
  <thread_id>` — Codex помнит контекст переписки.
- Запросы в одну и ту же рабочую директорию выполняются строго по одному
  (внутренняя блокировка), чтобы не было двух параллельных `codex exec` в
  одной папке.
- Полный JSONL-вывод каждого запуска сохраняется в `logs/<коллега>/`.

## Обновление

```bash
cd /opt/codex-team-gateway
sudo -u codex git pull
sudo -u codex venv/bin/pip install -r requirements.txt
sudo systemctl restart codex-gateway
```
