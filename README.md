# codex-team-gateway

Приёмная заявок на правки сайта для нетехнических сотрудников.

Человек из отдела продаж пишет обычными словами «поменяйте телефон на странице
доставки». Codex разбирается в коде, вносит правку в отдельной ветке, открывает
pull request и ждёт зелёных проверок. Сотрудник видит понятную карточку —
что изменилось, где это будет видно, что говорит автопроверка — и нажимает
«Выкатить на сайт». Дальше работает ваш обычный пайплайн: мерж в основную ветку,
вебхук, сборка, прод.

Один инстанс = один проект одного клиента. Всё, что отличает клиентов, лежит в
переменных окружения — код остаётся шаблоном.

---

## Как устроен путь заявки

```
заявка словами
   │
   ├─ Codex в отдельном worktree на ветке codex/req-N
   │    • читает AGENTS.md проекта
   │    • правит файлы, коммитит локально
   │    • не может пушить: у него нет доступа к GitHub
   │    • если непонятно — задаёт один вопрос человеку
   │
   ├─ Шлюз проверяет по git, что реально изменилось,
   │  пушит ветку и открывает PR
   │
   ├─ GitHub Actions гоняет обязательную проверку (`tests`)
   │
   ├─ Человек видит «было → стало» и жмёт «Выкатить на сайт»
   │
   └─ Шлюз мержит через GitHub API — branch protection остаётся в силе,
      вебхук запускает Dokploy, шлюз ждёт и показывает «Готово»
```

Ключевое разделение: **агент правит код, шлюз общается с GitHub, человек
принимает решение**. Codex физически не может смержить свою правку сам —
токена у него нет.

## Что видит клиент

- Список своих заявок со статусами на человеческом языке
- Живой ход работы: «Изучаю проект», «Правлю: delivery.html», «Прогоняю тесты» —
  без единой shell-команды на экране
- «Что изменилось в тексте» — было/стало по видимым строкам, чтобы правку можно
  было проверить глазами, не открывая GitHub
- Уточняющие вопросы агента прямо в карточке заявки
- Одну кнопку «Выкатить на сайт»

Картинки можно вставлять прямо в поле заявки (Ctrl+V), перетаскивать мышью или
выбирать файлом — до четырёх штук на сообщение, PNG/JPEG/GIF/WebP до 8 МБ.
Скриншот уходит в Codex вместе с текстом (`codex exec … -i`), поэтому «шапка
съехала на телефоне» можно не описывать словами, а просто показать. К ответу на
уточняющий вопрос картинки прикладываются так же.

Вход — по персональной ссылке `https://ваш-домен/?k=<токен>`. Ни логинов, ни
паролей: ссылку выдаёт администратор из встроенной админки.

## Требования к проекту клиента

1. Репозиторий на GitHub, ветка `main` защищена: прямой push запрещён,
   обязательна зелёная проверка (по умолчанию ищем check с именем `tests`).
2. Деплой из `main` уже автоматизирован (вебхук Dokploy или что угодно ещё) —
   шлюз ничего не деплоит сам.
3. В корне репозитория лежит заполненный `AGENTS.md` — правила того, что агенту
   можно и нельзя. Шаблон: [`AGENTS.md.template`](AGENTS.md.template).
   **Это главный предохранитель, не пропускайте его.**

## Установка через Dokploy

1. **Create Application → Compose**, репозиторий этот, ветка `main`,
   файл `docker-compose.yml`.
2. **Environment** — заполните переменные (см. таблицу ниже и `.env.example`).
3. **Deploy**. Первый запуск склонирует проект клиента в volume.
4. **Domains** → контейнерный порт `8787`, включите HTTPS. Порт наружу
   намеренно не публикуется: наружу сервис выходит только через домен Dokploy.
5. Откройте админскую ссылку `https://домен/?k=<ADMIN_TOKEN>` — там проверка
   конфигурации (виден ли репозиторий, есть ли право записи, авторизован ли
   Codex) и персональные ссылки для сотрудников.

### Переменные окружения

| Переменная | Обязательна | Что это |
|---|---|---|
| `PROJECT_REPO` | да | Репозиторий клиента, `owner/name` |
| `GITHUB_TOKEN` | да | Fine-grained PAT: Contents RW + Pull requests RW на этот репозиторий |
| `USERS` | да | Сотрудники: `anna:Анна Петрова,oleg:Олег Смирнов` |
| `ADMIN_TOKEN` | желательно | Ваш админский токен; иначе сгенерируется и будет виден в админке |
| `CODEX_API_KEY` | зависит | API-ключ OpenAI для автологина Codex. Без него — разовый вход аккаунтом ChatGPT (см. ниже) |
| `PROJECT_BASE_BRANCH` | нет | Основная ветка, по умолчанию `main` |
| `PROJECT_PROD_URL` | нет | Адрес сайта: ссылка «Открыть сайт» и проверка после выкатки |
| `PROJECT_HEALTH_PATH` | нет | Путь health-адреса, по умолчанию `/healthz` |
| `PROJECT_TEST_CMD` | нет | Локальный прогон тестов до пуша. Требует тулчейн проекта в контейнере |
| `GITHUB_REQUIRED_CHECK` | нет | Имя обязательной проверки, по умолчанию `tests` |
| `GITHUB_MERGE_METHOD` | нет | `squash` (по умолчанию), `merge` или `rebase` |
| `CODEX_SANDBOX` | нет | `workspace-write` по умолчанию |
| `CODEX_NETWORK_ACCESS` | нет | Сеть внутри песочницы, по умолчанию `true` |
| `CODEX_MODEL` | нет | Модель Codex |
| `MAX_CONCURRENT_RUNS` | нет | Сколько заявок обрабатывать параллельно, по умолчанию 2 |
| `BRAND_NAME`, `BRAND_SUBTITLE`, `BRAND_ACCENT` | нет | Как выглядит интерфейс у клиента |
| `DOKPLOY_URL`, `DOKPLOY_TOKEN`, `DOKPLOY_APPLICATION_ID` | нет | Точный статус выкатки вместо опроса health-адреса |

### Авторизация Codex

С `CODEX_API_KEY` контейнер логинится сам при старте. Если хотите использовать
подписку ChatGPT — выполните один раз в терминале контейнера:

```bash
gosu agent env HOME=/home/agent codex login --device-auth
```

Авторизация лежит в отдельном volume и переживает редеплой.

## Модель доступа

| Кто | Что может |
|---|---|
| Сотрудник клиента | Создавать заявки, отвечать на вопросы, подтверждать выкатку своих заявок |
| Администратор | Всё то же по всем заявкам + диагностика и ссылки доступа |
| Codex (`agent`) | Читать и править файлы своей рабочей копии. GitHub-токена, базы заявок и ссылок доступа не видит: работает под отдельным Unix-пользователем |
| Шлюз (`gateway`) | Пуш веток, открытие PR, мерж по нажатию человека |

Мерж делает GitHub, поэтому **правила репозитория работают всегда**: если
проверка красная или обсуждение не закрыто, кнопка вернёт отказ, а не обойдёт
защиту.

## Честные ограничения

- **Превью-стенда нет.** Человек подтверждает выкатку по резюме, списку
  «было → стало» и зелёной автопроверке. Живьём правку видно уже на сайте.
  Если результат не понравился — самый быстрый откат это новая заявка
  «верни как было».
- **Агент читает весь репозиторий.** Песочница ограничивает запись, а не
  чтение. Не держите в репозитории секреты в открытом виде.
- **Скриншоты уходят в OpenAI и остаются в volume.** Они часть заявки и её
  аудиторского следа. Если сотрудники снимают экраны с данными клиентов —
  предупредите их об этом заранее.
- **Один инстанс — один проект.** Несколько клиентов = несколько деплоев.
- **Тред заявки растёт.** Каждый уточняющий вопрос увеличивает контекст, поэтому
  длинные заявки лучше разбивать: одна заявка — одна правка.
- **Токен в ссылке.** Персональная ссылка и есть пароль. Access-log в контейнере
  отключён специально, но ссылку нельзя пересылать в общие чаты.

## Разработка

Бэкенд:

```bash
uv venv --python 3.12 .venv
uv pip install --python .venv/bin/python -r requirements.txt
.venv/bin/python tests/e2e.py          # сквозной прогон без GitHub и без Codex
```

Интерфейс — React 19 + [HeroUI v3](https://heroui.com) + Tailwind CSS v4, собирается Vite
в каталог `static/`, откуда его отдаёт FastAPI (отдельный веб-сервер не нужен).
`static/` не хранится в репозитории — его собирает Docker при сборке образа:

```bash
cd web && npm install && npm run build   # разово, чтобы открыть интерфейс локально
npm run dev                              # разработка: vite на :5173, API проксируется на :8799
```

`tests/e2e.py` поднимает локальный bare-репозиторий вместо GitHub и заглушку
вместо Codex, прогоняя весь путь заявки: вопрос → правка → PR → выкатка.

Посмотреть интерфейс на демо-данных:

```bash
DATA_DIR=/tmp/gw-ui .venv/bin/python tests/seed_ui.py
DATA_DIR=/tmp/gw-ui USERS="anna:Анна" ADMIN_TOKEN=demo PROJECT_REPO=acme/demo \
  .venv/bin/uvicorn app.main:app --port 8799
```

### Структура

| Файл | Назначение |
|---|---|
| `app/pipeline.py` | Жизненный цикл заявки, промпт для агента |
| `app/codex_runner.py` | Запуск `codex exec --json`, перевод событий на человеческий язык |
| `app/gitops.py` | Worktree на заявку, факты об изменениях по git, пуш |
| `app/github.py` | PR, статусы проверок, мерж |
| `app/deploy.py` | Ожидание выкатки: Dokploy API или health-адрес |
| `app/auth.py` | Люди и персональные ссылки |
| `app/uploads.py` | Картинки к заявкам: проверка, хранение, передача агенту |
| `app/main.py` | HTTP API и админка |
| `web/src/` | Интерфейс на HeroUI: список заявок, карточка заявки, админка |
| `web/src/status.ts` | Единая таблица статусов: человеческие подписи и шаги |
